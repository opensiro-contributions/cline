## Precise Cline runtime boundary and S4 function

Original immutable [cline/cline main@20b042723a14412f6c1e84230b008708534d6e8c](https://github.com/cline/cline/commit/20b042723a14412f6c1e84230b008708534d6e8c), reviewed 2026-11-20. Narrow P0: one Cline **Hub recurring schedule** (named schedule_id and its workspaceRoot), not a blanket VS Code, cloud-session or global provider policy. S4 investigator owns *prospective* retain/migrate/hold choice based on a source-attributed dated model/provider notice. The current Cline schedule owner applies only a policy-allowed choice via a separate interactive decision. Hub/cron executes next run; run status and **actual provider/model** must return for later prospective adjustment.

**Ownership/control:** a Cline agent can evaluate future alternatives, but Cline's first-party built-in schedule mutations explicitly require an interactive user session. Background scheduled agents are noninteractive; they CANNOT directly use `tasks.scheduled.update` to change an existing schedule. Preserve this first-party guard, workspace scope, tool permissions and any parent veto. S1 task executions, S2 multi-agent conflict control, S3 current schedule/worker commitments, optional independent S3* outcome review and S5 parent identity remain distinct. Do not infer that a simple deprecation filter is S4, that scheduled task status is S3* independent audit, or that a parent gate transfers ultimate S5 decisions.

**Counterfactual:** delete the optional S4 choice-maker but keep Cline catalogue, schedules, `tasks.scheduled` and Hub: the user can still manually choose a new model. Distinct autonomous *future-oriented option selection* disappears. If approved proposal cannot change subsequent operation or no actual outcome can return, the proposed S4 chain is incomplete.

## Native Track B: minimum combined C-construction

**Candidate A: generic hosted model strategy controller and typed Host mutator. REJECT as oversized.** Cline already has a narrower first-party `model_selection` write to schedules; no reason to add a global unscoped provider switch.

**Candidate B: scheduled future-notice alert only. REJECT as S4 C closure.** A model deprecation summary cannot show an autonomous alternative choice, real authorized later-operation effect and feedback.

**Selected candidate C: schedule-native prospective transition.** Use existing Core automation to run an optional S4 investigator over a bounded model/provider notice dataset. The agent reads an externally dated notice, a named schedule's `modelSelection` and available catalog candidates; it emits a proposal `{scheduleId, workspaceRoot, fromProvider/fromModel, toProvider/toModel, choice: retain|migrate|hold, evidence, observedAt, expiresAt, rationale}`. **These fields are PROPOSED research artifact fields, not an existing Cline API.** For retain/hold, no schedule mutation. For migrate, a legitimate interactive session presents the proposal to its owner, checks prior consent and scope, and uses **existing** `tasks.scheduled.update` `model_selection` with a matching `schedule_id`. [`HubScheduleService.updateSchedule`](https://github.com/cline/cline/blob/20b042723a14412f6c1e84230b008708534d6e8c/sdk/packages/core/src/cron/service/schedule-service.ts) stores the change. Next scheduled [`CronRunner.buildStartRequest`](https://github.com/cline/cline/blob/20b042723a14412f6c1e84230b008708534d6e8c/sdk/packages/core/src/cron/runner/cron-runner.ts) reads the scheduled model; S4's next observation reads correlated execution feedback and can revise the future plan.

**Smallest actual source-specific uncertainty/delta:** the native scheduling mutation/effect path is **already built**. The missing C sufficiency is not a new generic write interface; it is (a) a source-backed autonomous S4 proposal and owner-visible choice/handoff for a named Cline schedule, and (b) a **read-only, reliable proposal → authorized schedule revision → actual scheduled-run model/outcome correlation** accessible to that S4 investigator. Investigate whether existing `listScheduleExecutions().sessionId` plus existing session model and schedule history already suffice; if yes, implement *no new history port*. Only if the join is insufficient add the narrowest read-only projection in `schedule-service.ts` / `schedule-tool.ts`, and an execution-model snapshot in `cron-runner.ts` when unavoidable. Do not add a new metric, all-purpose VSM control class, extra automatic S5 policy or hidden scheduled-task mutator. This is a **proposal**, not a claim of implemented code or a passing session-level permission check.

**Authority choice:** the S4 autonomous agent decides what *future option* to propose; the parent/user decides whether the corresponding scheduled task may change. Cline's interactive and same-workspace guards are mandatory. Headless scheduled agents do not have permission to call the mutating built-in tool. No secret grant of automation rights; without an interactive parent the choice remains a pending proposal, and this is honest S4→S3 feedback limitation, not a GO for unattended model switching.

**Independent counterfactual:** would a hard-coded catalog refresh + existing schedule tooling, without the proposed autonomous investigator, still make the same external-future option decision with similar discretion and later correction? If yes, NO_GO for this S4 candidate. If the proposed investigator cannot observe the actual applied model after a later run, the entire S4=C hypothesis is unclosed pending construction/validation. A passing `schedule.update` response alone is not subsequent-operation feedback.

| Falsifiable native experiment | Expected legitimate effect/return | Failure that stops C claim |
| --- | --- | --- |
| Two distinct dated external notices for the *same schedule* | Optional S4 agent selects different lawful retain/migrate/hold options with traceable evidence; model candidates match first-party catalogue | Only deterministic deprecated warning; invalid/stale/fictional future input |
| Authorized schedule update | In an interactive matching-workspace session, owner approves named `schedule_id`, `tasks.scheduled.update` accepts `model_selection` and HubScheduleService readback reflects it | Wrong workspace, no parent approval, wrong schedule or silently changed global model |
| Disallowed schedule edit | A noninteractive scheduled run attempts `tasks.scheduled.update`; operation is rejected; no mutation | Background actor acquires mutation authority or bypasses interactive guard |
| Later run closure | Following dispatch starts using the committed provider/model; `executionId/sessionId/status` and actual model return to proposed S4 state through proven history/session lookup | Only accepted update but no later run or no actual model provenance |
| Concurrency and compatibility | Already-running session retains original model; new schedule revision applies only to subsequent dispatch; invalid/revoked candidate and absent actor retain baseline | In-flight model substitution, unintended schedule rewrites, stale proposal wins |

**P0:** smallest complete lawful future-choice → approved schedule action → real run feedback chain. **P1:** model/notice compatibility and timestamp, parent/workspace/interactive gate, proposal-to-execution join and original-native tests. **P2:** NONE. **Verdict:** GO / NEEDS_EVIDENCE for a PROPOSED C constructor only, not shipped evidence. **Primary falsifier:** no distinct autonomous future choice, impossible lawful effect/return, or already equivalent first-party closed S4 path.
